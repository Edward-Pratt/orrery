# agent (orrery-agent)

A Node service on a remote Host. It dials out to the hub with its token and runs that Host's Factorio server: RCON,
the Factorio mod's events, the server's unit, saves, host samples, game updates and its own deploys (`update`,
`updateResume`, `updateCancel` and `deploy`, from `agent-v1.1.0` on: release 2 in `docs/ROADMAP.md`; the hub's side is
built separately against the same contract, and refuses both for an older Agent), and its game settings (`settings`
and `settingsSet`, from `agent-v1.2.0` on: `docs/notes/factorio-world-settings.md`, stage A). Node 24+ + TypeScript, run directly (type stripping, no build step) like the hub. No runtime
dependencies: Node built-ins only (game tarballs go through the Host's `xz`, which setup installs).

```bash
npm test            # node --test "test/*.test.ts"
npm run typecheck   # tsc, noEmit; also type-checks the hub types src/ imports
node src/index.ts           # the agent (orrery-agent.service)
node src/index.ts check     # the first-boot check: a report on stdout, line by line, exit 0 when nothing failed
```

On the Host it reads `/etc/orrery-agent/config.json` and, for game updates, `/etc/orrery-agent/image.json` (`{ image,
glibc }`, both written by `deploy/setup-agent-host.sh`), and the environment `ORRERY_AGENT_TOKEN` and `RCON_PASSWORD`
(root-only env files read by systemd). For tests and the local dev loop only, `ORRERY_AGENT_CONFIG` moves the config
file (and `image.json`, read from beside it) and `ORRERY_AGENT_ROOT` the agent's folder (`/srv/orrery-agent`).

## Wire contract

`docs/protocol.md` ("Agent connection") is authoritative. The message types come from `hub/src/types.ts`, through
`import type` only: a release tarball is `agent/` alone, so no runtime import may leave `agent/`. `src/wire.ts` holds
the agent's copies of `PROTOCOL_VERSION` and `LIMITS`; `test/wire.test.ts` checks them against
`hub/src/protocol.ts`, so change them together. `src/update.ts`'s `GAME_MODS` (the game's own mods, for an update's
`to`) is a copy of `hub/src/factorio.ts`'s, checked by `test/update.test.ts`. One line on the Agent port is at most 1 MiB (`LIMITS.lineBytes`,
set on 2026-10-31 while the owner was away: `docs/adr/0004`), its `\n` included, both ways.

The release is `agent-v` + `package.json`'s `version`, which stays `0.0.0` in the repo (like `factorio/info.json`):
the hello's `agentVersion` and the `connected` file carry it, and an agent deploy (`deploy`, run by
`deploy/deploy-agent.sh`) is `ok` only when it matches the tag: the script's gate compares the `connected` file's
`version` with the tag, and its rollback's with the release folder `current` pointed at before.

## TypeScript constraints (type stripping)

- Erasable syntax only: no `enum`, `namespace`, or constructor parameter properties.
- Relative imports include the `.ts` extension; type-only imports use `import type` / `type X`.

| `src/hub.ts` | `HubClient`, the two connections to the hub's Agent port. The Agent connection sends `agentHello` and nothing else before `welcome`; then a `ping` every 10 s, `serviceState`, `saves`, `installed`, `events` (whether game events reach the hub, its `reason` `printable` and cut to 2 KiB) and `settings` (`GameSettings`' report: its `problem` and `rolledBack` `printable` and cut to 2 KiB, its lists to the hub's limits; never twice the same on one connection) on connect and on each change (`installed` never twice the same in a row, and kept in `<state>/installed.json`, read back shape-checked at start, so a restarted agent sends it on connect while its server is stopped too; `latestInstalled`, for a game update's `from` and `to`), then the `welcomed` hook (a game update's latest step and pending `updateDone`, a deploy's outcome not yet sent), `hostSample` when given (never queued), `send` for a game update's steps (false while not connected), `deliver` for `updateDone` and `deployResult` (resolves true only once the line's write succeeded; false while not connected, when the write fails, or after 30 s: the caller keeps it and sends it again on each connect, and the hub ignores a repeat), and a `reply` by id to every request: a `Handlers` entry's result (a rejection's message as its `error`, `redact`ed and cut to 2 KiB), or `ok: false` for one that is invalid, of an unknown type or has no handler. A hello the hub refuses as `reconnecting too fast` (under 5 s after its last welcome, `HUB_WELCOME_GAP_MS`) counts no failure and is logged without `(rejected: `, which the first-boot check stops at: the next hello waits what is left of those 5 s since the last welcome it saw (all of them before its first), and a twentieth more (`tooFastWait`). After each welcome it writes `<root>/connected`, `{"version":"agent-vX.Y.Z","time":<epoch ms>}`, atomically (temp file and rename; `writeAtomic`): exactly what `deploy-agent.sh`'s gate reads (`version` equal to the tag; the script removes the file right before each restart, so `time` is never compared). The game connection opens only while the Agent connection is up, RCON answers (`status`) and the unit, if its state is known, is active: `hello` with the agent's token and the orrery mod's version, `started` once per run of the unit (its change time, kept in `<state>/started.json`, so a restarted agent doesn't announce a run again), then a `heartbeat { tps: UPS, players, paused }` per answer once there is a rate, each game event given to `event` and each `backup` (dropped while the game connection isn't up, as a Mod drops them while disconnected); the hub's `say`, `notice` and `linkResult` on it go to `toGame`, a `cmd` to `command` (answered by `cmdResult`, also with a `refused` line for one that isn't valid, so the hub never waits; a failure is "the command did not run", but one sent and not answered in time, `RconNoAnswer`, "may still run"), `save` to `save`. The stopping rule: for a stop the agent started (`stopping`, from `serviceAct` stop or restart) it sends `stopping` and closes at once; any other end of a run is `RunWatch`'s, at the unit's final state: `stopping` then the close for `stopped`, the close alone for `crashed`. A stall (`stalled`), or RCON gone (`down`) while the unit is still active, only stops the heartbeats, so the hub's hung detection reports a frozen server as hung; with no unit state known, `down` closes it. After a run ended no game connection opens until the unit's next run (active with another change time). It also closes with the Agent connection; `gameUp` says whether it is welcomed (a game update's gate). A game `hello` the hub refuses (`reconnecting too fast` among them) closes only that connection: the next RCON answer (`status`) opens another, as many times as it takes, so an update's gate, which polls `gameUp` for its 5 minutes, never gives up after one. A line from the hub over the cap destroys that connection (then a reconnect). `stop`: `bye`, then once it is written the game connection and the Agent connection end, 2 s at most. |
| `src/status.ts` | `StatusPoller`: `/orrery-status` over one kept RCON connection every 5 s; `status` (the `Reading`, and the `Status` it came from: version and mods, for a game update and `installed`) after each successful round trip only (heartbeats follow RCON, never a timer); `stalled` once when RCON takes the connection but times out (an `RconTimeout`: a blocking save, or frozen) or answers without a status; `down` once when it is gone (refused, reset or closed by the server). `players` is the latest online list (emptied once RCON is gone). `parseStatus` reads the mod's reply as untrusted: anything off is no status; players `{}` is nobody; names over 64 characters or with a control character dropped, at most 200; versions must be `X.Y.Z`; the orrery mod's from `mods.orrery`. `reading`: UPS = Δtick / Δwall time (null on the first answer or a tick that went back); paused when `tick_paused`, or nobody on with `auto_pause`, or Δtick at most 1 with players on. `auto_pause` comes from the `autoPause` option (`GameSettings.autoPause`: what the running server started with, since the file may hold a value saved for the next start), else from `readAutoPause`, which reads `server-settings.json` (container-writable) with `O_NOFOLLOW` and `O_NONBLOCK`, only a regular file up to 1 MiB, `auto_pause === true`, else false (the first-boot check reads it so too). |
| `src/settings.ts` | `GameSettings`, a factorio server's game settings: `<data>/config/server-settings.json` and `server-adminlist.json`, each read through the config folder opened once (`O_DIRECTORY`, `O_NOFOLLOW`) as `files.ts`'s `openPlain` (a regular file on that folder's filesystem, 1 MiB at most), as untrusted files that drive display only. `parseSettings`: each managed key (`KEYS`) by the hub's rule (`settingsFieldOk`), one left out as Factorio's default (but `name`, `description` and `visibility`, which Factorio needs), `allow_commands` only as a string (Factorio 2.1.24 refuses a boolean there); one that fails makes the model null and `problem` names the key, never a value; other keys (not `_comment…`) are `extra`. `parseAdmins`: the names that pass the rule, each once whatever its case, 100 at most. `report` (the `settings` push, `game_password_set` only, never the password) on `start`, `refresh` (each welcome), after its own writes and when a start's file was read; pushes go out in order. `set` (`settingsSet`), one at a time (`busy` while one runs or waits: a game update, a restore and a deploy are refused meanwhile): `ready` (no game update, no deploy), then a fresh `systemctl show`, refused while activating, deactivating or reloading; the password the request's (null: none), else the file's, refused if the rule refuses it ("The file's game password can't be kept: set a new one."); refused: verification off with no password, an admin twice in any case, a new name over 50 bytes (`NAME_BYTES`, `GAME_SETTINGS.nameBytes`: Factorio 2.1.24 keeps no more), a broken UTF-16 character. Then `renderSettings` (`JSON.stringify` of a new object: the managed keys, `visibility` false and false, `non_blocking_saving` false, its own `_comment`; no username, token or admins) written through the folder handle as `.<file>.<random>.partial` (`O_CREAT`/`O_EXCL`/`O_NOFOLLOW`, mode 600), synced and renamed over the file; the start gate armed and `rolledBack` cleared. With it stopped: no RCON; the adminlist written the same way, lowercased, when it differs. The reply is `{ applied, pending }` (pending: the failed ones and the restart-only keys, `auto_pause` and `autosave_slots`, that differ from what the run started with), then the push. `StartGate`'s `start` reads the file as `startedWith` (kept with the run's change time, so an agent restarted during a run keeps it), emptying the failed ones; its `good` makes that `lastGood` when fully readable (a password the rule lets through), and so does its `late` while there is no `lastGood` yet (an agent deployed onto a server that has run past 300 s: its `startedWith` is the file as read at the agent's start); its `failed` writes `lastGood` back as a write does (none: nothing written) and sets `rolledBack` to the time and Factorio's last `Error` line from `factorio-current.log` (`printable`, 2 KiB). `<state>/settings.json` (mode 600: it holds `lastGood`'s password) keeps `lastGood`, `startedWith`, the gate's arming time, the failed keys and `rolledBack`, written whole after each change and read back shape-checked. `start` removes partial files an exit left in the config folder. Never logs a value: key names only. |
| `src/gate.ts` | `StartGate`, the server's starts from the unit's states (`service`) and RCON's answers (`rconUp`): `start` when the unit becomes active (or its change time moves while active; the first reading counts), `good` when RCON first answers in that run within `GOOD_WITHIN_MS` (300 s, `TimeoutStartSec`) of its change time, `late` when it first answers past that (a run the agent came to later, or a slow load: never judged good), each `gated` when it was the start the gate watched, which disarms it (a late one too: that run crashing later is no failed start). | `src/events.ts` | The Factorio mod's game events, both ways (factorio/CLAUDE.md). `GameEvents`: a UDP listener on 127.0.0.1:`agentUdpPort` (retried every 10 s while the port is taken) that takes datagrams only from 127.0.0.1:`factorioUdpPort`, only while the unit is `active`, and after each start (it became active, or its change time moved while active: a restart between two readings) only once `factorio-current.log` (`files.ts`'s `head`: a regular file, its first 1 MiB, whole lines) has Factorio's engine line `Opening socket at (IP ADDR:({127.0.0.1:<port>}))` followed by a line that is not `Closing socket`, and no `Opening Lua UDP Socket failed` (`socketState`, the Opening line `openingLine`: Factorio writes the Opening line before it binds, so on a taken port it is followed by `Closing socket`, `Socket closed` and the failure line, as seen on 2.1.24), so no other local process bound that port first. A log not written since the agent saw the unit stopped (inactive, failed or activating), or for an unseen restart since the second after it became active, is the previous run's and is read again (every 1 s) until Factorio replaces it. The failure line, the Opening line followed by `Closing socket`, or no decision within 60 s: events are off until the next start, logged once. `state` (`EventsState`) says on each change whether events reach the hub, for the Agent connection's `events`: off, with why, once the gate is off or while the UDP port can't be listened on past one retry; on once the gate is on and the port listened on (the first decision since the agent started counts as a change). Over 4 KiB, or not the mod's shape (`parseDatagram`: `t`, `seq` a safe integer, each field checked against the hub's limits and copied; `message` and `text` cut to 1 KiB): dropped, each kind logged once per start. A `link`/`unlink` for a name not in `StatusPoller.players` (up to 5 s old: the player may have just joined) waits for a fresh `/orrery-status` on the command connection (never a UDP `join`), and is dropped, each one logged (its name `printable`), unless that has them online. `seq` gaps (and going back) are logged; the baseline is the mod's `hello` datagram, asked for with `/orrery-hello` once per start after the gate opens and RCON answers (`rconUp`); one that doesn't come within 5 s is logged. Emits `chat`, `join`, `leave` (no `reason` on the wire), `death` (`deathMessage`: "Alice was killed by Bob", "… by a medium biter", "Alice died"), `milestone` and `link` (`uuid` `""`), `unlink`, within `EventBudget`: 5 a second sustained and 30 at once, all kinds together (a cell-rate check on a monotonic clock), so a chat flood can never push the game connection past the hub's 20 lines a second, which it closes after 10 s; only events count, not the hello or a datagram dropped as malformed, and a link or unlink counts before its fresh `/orrery-status`, so a flood of them can't flood RCON. One over the budget is dropped (its `seq` still taken, so no gap is logged) and counted: the first drop starts a minute, at whose end one line logs the count (`stop` logs what is counted). `toCommand`: `say`, `notice`, `linkResult` as `/orrery-say {author, message, source}`, `/orrery-notice {message}`, `/orrery-reply {player, ok, message}`, the argument `commandJson` (`JSON.stringify`, plus `\u` escapes for DEL, the C1 controls and U+2028/9): one line, never Lua. `toGame` runs one and logs a failure or a reply that is not `{"ok":true, …}`. |

| `src/logs.ts` | `Logs`, the logs the hub may read, by fixed name only (a name from the hub is looked up in the list, never joined into a path): `list` (`logs`: each of `factorio-current.log` and `factorio-previous.log` in the server's data folder and `agent.log` in the agent's, `{ name, size, modified }`, if there as a regular file); `log(name)` (its last 1000 lines); `journal(unit)` (the last 200 lines of the unit's own log file: `factorio-current.log` for the server's unit, `agent.log` for `orrery-agent.service`; any other unit refused, since the agent's user may not read the system journal). | `src/saves.ts` | `Saves`, Factorio's `saves/` as Backups. no restore of this agent runs yet. ## Trust boundaries (do not weaken)

- The agent never runs a path or argv it received from the hub. Every request maps to a fixed operation on its own
  configured unit, folders and file names, and a name is checked against the agent's own listing.
- What the hub sends is checked like the hub checks what it gets: documented fields only, each within its limit,
  and a line over 1 MiB closes the connection. Every line the agent sends fits the hub's limits too.
- RCON output is untrusted, and so is every file under the server's `data` folder (the container writes it): they
  drive display and alerting only, never a path or a security decision. Such files are opened without following
  symlinks or blocking, and read only if they are small regular files.
- Game events come over UDP only from Factorio's own Lua UDP port, only while the unit is active, and only once
  Factorio's log (this run's, not the previous one) shows Factorio bound that port; a `link` or `unlink` only for a
  player online at the latest `/orrery-status` (a fresh one if the last poll's list lacks them; never a UDP `join`). Every field is checked against the hub's limits before it is sent.
- RCON commands the agent builds are the mod's own commands with one line of JSON as the argument, and Factorio's
  built-ins `/config set <option> <value>` (the option from a fixed table in `settings.ts`, the value one it validated:
  one line, printable, within its field's limit), `/promote <name>` and `/demote <name>` (the name checked against
  `^[A-Za-z0-9_.-]{1,60}$`). These were checked on 2.1.24 not to flag the save. The first-boot check also sends the
  built-in `/help`. Never Lua, never `/c` or `/sc`, which would flag the save for good.
- The game settings files (`server-settings.json`, the adminlist) are container-written: they drive display only. What
  the agent writes there comes from its checked fields alone (never public, never on the LAN, no factorio.com
  credentials), through the config folder opened without following a link; the game password goes only into that
  file, its own `<state>/settings.json` (mode 600) and its one `/config set password` command: no log line, reply,
  push or error carries it.
- The agent's own state lives under `/srv/orrery-agent`, which the container never mounts; the config refuses server
  folders that overlap it.
- `serviceAct` acts on the agent's own configured unit only: the verb is all it takes from the request, and systemctl
  runs through `execFile` with `--no-block --` before the unit, never a shell.
- What the agent deletes or writes in `saves/` (pruning, a restored copy) goes through that folder opened once without
  following a symlink, so a `saves/` the container swapped for a link can't point it elsewhere. A restore copies from
  the open handle of a listed regular file, only while the unit is stopped (read again before the copy gets its
  name), and never overwrites a file.
- `deploy` starts one fixed unit, `orrery-agent-deploy@<tag>.service`, for a tag checked against `^agent-v\d+\.\d+\.\d+$`
  (the only part of the request it uses), through `execFile` with `--no-block --` before the unit; polkit allows
  factorio exactly that start, and the script it runs is root-owned and checks the tag again. A tag from
  `deploy-status.json` is checked the same way before it names a unit, and a `deployResult`'s log is `redact`ed.
- Everything the agent logs, to the journal and `agent.log`, has URL query strings stripped (`redact`): a signed
  download link's credentials never reach a log.
- A game update's input is checked like any other (`checkUpdate`): versions, names and URLs; downloads come only from
  `ALLOWED_HOSTS` over https, redirects included, each capped in size and stopped after 60 s without a byte. The agent takes no hash on the hub's word: the game's from
  factorio.com's sha256 list, each mod's from the mod portal's public API, and a mismatch fails prepare. Nothing is
  staged in `/tmp`; a release is unpacked by the agent's own tar reader, never through a path or link that leads out,
  and a binary needing a newer glibc than the image never becomes a release. `current` only ever points at a validated
  `releases/X.Y.Z`. The update's bookkeeping is `<state>/update.json`, in the agent's folder: no file under the data
  folder decides anything about an update but which of the release's own (sha256-checked) mods stay on, as the
  server's current `mods/mod-list.json` has them (the container sets that list for the running server anyway; read
  without following a link, a list that isn't Factorio's fails prepare), and no step detail, reply error or log line carries a query string.
- Whatever RCON or a container-written file puts in a line the agent logs or reports (a reply, a save or mod name, a
  log line) is `printable` first, and a save or player name that isn't is dropped: it can neither forge a line of
  `agent.log` nor drive the terminal that shows the first-boot report.

Keep timing-sensitive tests on small timeouts, not sleeps of seconds; stop every poller and client in `t.after`.
Times are relative to `Date.now()` (or a fake clock), never a fixed date, so no test turns red on a later day. A
test never races a timer of the code's: it waits for what the code shows (a message, a log line), gives a timer it
must not see fire a wide margin, and asserts only lower bounds on how long a timer took (a busy machine makes timers
late, never early).
