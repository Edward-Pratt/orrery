# hub (orrery-hub)

Node 24+ (tested on 24.21 and 26.9) + TypeScript + discord.js 14. Node runs `.ts` directly (type stripping) — there is no build step.

```bash
npm test            # node --test "test/*.test.ts"
npm run typecheck   # tsc, noEmit
npm run check-config   # validates ./config.json (or -- <path>) offline; same rules as startup
npm start           # node src/index.ts; reads ./config.json (or argv[2]), env DISCORD_TOKEN (only with integrations.discord)
                    # and DISCORD_CLIENT_SECRET (only with integrations.web), GITHUB_TOKEN (with integrations.github; also lets the library fetch Actions artifacts)
```

## TypeScript constraints (type stripping)

- Erasable syntax only: no `enum`, `namespace`, or constructor parameter properties.
- Relative imports include the `.ts` extension; type-only imports use `import type` / `type X`.

## Modules

| File | Job |
|---|---|
| `src/protocol.ts` | Validation of the wire messages (their types are in `types.ts`, re-exported here): a schema per message type, checked to have exactly its type's fields, with a limit on every field (`LIMITS`: player names 64, messages 1 KiB, `players[]` 200, `output[]` 500 lines of 1 KiB, `detail` 2 KiB, `saves[]`/`mods[]` 500, `reply.data` 256 KiB as JSON, any other string 256; the same on both ports); over a limit the message is refused, but a command's `output` and a `backup`'s `detail` are cut to fit (Mods already deployed send up to 2000 lines of any length). `LIMITS.lineBytes` (1 MiB, the newline not counted) is the Agent port's line cap, for its line reader. `parseModLine` for a game connection (a Mod's, or an Agent's for its server: `milestone`, `heartbeat.paused`), `parseAgentLine` for the Agent port (`agentHello`, a game `hello` as a first line, and the Agent connection's messages), `parseReplyData(request, data)` for an ok `reply`'s data (`journal`/`log`: 1000 lines of 1 KiB; `logs`: file entries). Each returns a new object of only the schema's fields, nested ones too, or null; a `reply`'s `data` alone is only size-checked (one too deep to serialise is refused), so nothing reads it before `parseReplyData`. `PROTOCOL_VERSION` is shared by the Mod's hello and `agentHello`. The contract with the mod and the Agent. |
| `src/agents.ts` | `Agents` (with `integrations.agents`): the Agent port, a second listener on `listen` (`start` resolves once it is bound; while its address isn't on this machine yet, EADDRNOTAVAIL, it tries again every 10 s, logged once, and startup never waits for it). A connection is paused at accept and destroyed without a word unless its peer address is a configured Agent's and has fewer than 4 open (`PEER_SOCKETS`, handshaken or not; the fifth logged at most once a minute), so nothing is read first; its lines are read from raw chunks with `LIMITS.lineBytes` as the cap (a longer one destroys it) and the line budget (`LINES`, a token bucket: 20 lines/s in bursts of 100; lines over it are dropped, and a connection still dropping 10 s on is closed), before and after the handshake, then each parsed message within its type's budget in that connection (both budgets kept per connection, not per socket: the Agent connection's by its Agent's id, the game connection's by its server's, a first line's by its peer address, so a reconnect goes on with what the last one left; `TYPES`: game events together 2/s in bursts of 30, `link`/`unlink` 1/s in 5, `updateStep` 5/s in 20, `serviceState`, `saves` and `installed` each 1/s in 10 and dropped when deep-equal to the last one of their type passed on (`SAME`), `heartbeat` 1/s in 5, `backup` 1 per 10 s in 3, `events` 1 per 10 s in 3 taken only by a change; others only the line budget, none of which posts or stores per line; over it dropped, the connection kept; and `NEW_PLAYERS`: a heartbeat's names not on its server's player list yet, 1 per 10 s in bursts of 200, a name over it left out of that heartbeat, so churning names, or reconnecting (the list is empty while offline), can't make playtime sessions faster), drops logged at most once a minute with a count; the one table of the Agent port's budgets (docs/protocol.md, "Rate rules"); a line whose handling throws ends only its own connection. Its first line, within 5 s: an `agentHello` (an id in config whose `address` is the peer's, its token by `timingSafeEqual`, the protocol in range; a second connection replaces the first) or a game `hello` (that Agent's token, for its own `server`, while its Agent connection is up), whose lines it then parses with `parseModLine` and hands, within their budgets, to the handler `ServerHub.attach` returns (`cmdLate`, `quest` and `achievement`, which an Agent never sends, dropped: `NOT_FROM_AGENTS`); either refused (`reconnecting too fast`) under 5 s after the last one of its kind for that Agent was welcomed (`HANDSHAKE_MS`, exported: the agent's tests check its copy), the live one kept; else `reject`, then the connection is ended and destroyed within 2 s whatever the peer does. The registry (`get`, `list`: connected, and the version its latest `agentHello` named). An Agent with no line for 20 s, or whose connection closes without `bye`, is lost: `ServerHub.agentDown` (its server `lost`), one `agentLost` host notice, then `agentBack` when it connects again; after `bye` only `agentDown`. An Agent's `events` (whether its server's game events reach the hub) posts an `eventsOff` host notice (its `reason`) or `eventsOn` only when it changes what the hub last heard from that Agent (kept while it is away), so its send on every connect posts nothing. `request(id, call, { timeoutMs })`: typed RPCs with a fresh id and a 30 s timeout unless the call gives its own, an ok reply's data through `parseReplyData`; rejected when not connected, refused (its `error`), late, malformed or cut off. Events (typed): `agentLost`, `agentBack` and what an Agent pushes (`serviceState`, `saves`, `installed`, `updateStep`, `updateDone`, `deployResult`, each the parser's schema-only copy); a `hostSample` goes to its Host's `HostMonitor` (`Hosts`, by the Agent's id), at most one per 10 s per Agent across its connections (`SAMPLE_MS`), its `ts` replaced by the hub's clock. Its throttles by the hub's clock (handshakes, host samples, drop logs) treat a time before their last stamp, a clock stepped back, as long after it. `AgentsOptions`: shorter timings (`handshakeMs` too) and the line budget, for tests. Hub core. |
| `src/servers.ts` | `ServerHub`: the Mod port (`listen`) and the Agents' game connections (`attach(socket, serverId, modVersion)` from `Agents`, which keeps reading the socket and feeds the returned function its messages, parsed and within their budgets; the socket joins those `close` destroys), per-server state, liveness (crash/stop/hung; `started` once per connection, a repeat on it ignored; `start()`, which `startHub` always calls, runs hung detection and the 60 s grace period, after which a factorio server whose Agent isn't connected stays unknown), the Agent rules (`agentUp`/`agentDown`: an Agent leaving drops its server's game connection and makes it `lost`; a game connection closing without `stopping` while its Agent connection is up waits `settleMs` (5 s) for that one to close too, else it crashed; hung detection is off only while a factorio server's Agent is away; a factorio server's lifecycle events at most 20 an hour, in bursts of 20, kept across connections: one over it is not emitted at all, so the uptime log, the stream and Discord alike miss it, the drops logged at most once a minute with a count, and the latest dropped one is emitted when the next token comes, within 3 min, unless a later one went out first; a Mod's server has no such budget), `say`, `broadcast(id, text, by)` (a hub line in game, such as a countdown's: a Mod's server runs `say <text>` through `runCommand`, audited as `by`; a factorio server's Agent gets a `notice`, cleaned like `say`, and builds the game's command itself), `backup(id, by)` (a Backup now: a Mod's server runs `backup start` through `runCommand`, resolving with its output; a factorio server's Agent gets `save`, audited as `backup`, resolving with none; the game's `backup` event follows either way), `runCommand` (control characters taken out; a Mod's command without a leading `/`, a factorio server's as typed, `/players`, and at most 256 characters, as its Agent runs no longer one: else `CommandRefused`, before it is audited or sent), `audit` (entries go to the `HubOptions.audit` sink: the database), `event` emitter (game, lifecycle and hub-core `notice` events, plus `say` for chat sent in game, with its `source` (`discord` or `dashboard`, the latter with the admin's avatar URL, never sent to the mod), `console` for command output, late output included, `tps` when a heartbeat's TPS moved by 0.1 or more, and `paused` when a heartbeat changed the server's `paused`), `publish` (hub-core modules put typed notices — kind, severity, details — on it), `modVersion` (what a server's Mod reported in its latest hello, kept after it disconnects), `paused` on each `ServerState` (from an Agent's heartbeat: while paused the rate is ignored, not put on the state or the stream, but heartbeats still count for hung detection), and `publishTarget` for notices about the host, a service, a check or a deploy (`target` events, apart from server `event`s so server handlers never see them). ## Trust boundaries (do not weaken)

- Mod input: every line goes through `parseModLine` (checks `Object.hasOwn` on the type, field types and every
  field's limit, and returns a copy holding only the schema's fields); Agent port input through `parseAgentLine`.
  Tokens 16–256 chars (an Agent's 32–256), compared with `timingSafeEqual`. The Mod port and the web API bind `127.0.0.1`.
- Agent port (`agents.ts`): it binds only `integrations.agents.listen` (the tailnet address); a peer that isn't a
  configured Agent's address is destroyed before a byte is read (both first lines); every line is capped at
  `LIMITS.lineBytes` and rate-limited, before and after the handshake, and each message type has its own budget per
  connection (`TYPES`; host samples one per 10 s per Agent, stored with the hub's clock; a heartbeat's names new to its
  server within `NEW_PLAYERS`), both kept across reconnects
  (never a fresh burst), and each kind of connection welcomed at most once per 5 s per Agent; its server's lifecycle
  events (each a never-pruned uptime row) at most 20 an hour (`ServerHub`, by server id, across reconnects); at most 4 connections at once
  per address, and a refused one is destroyed within 2 s; an Agent speaks only for its own `server`, and
  its game connection is accepted only while its Agent connection is up. A `reply`'s data is read only through
  `parseReplyData` for the request it answers.
- Discord → MC: `ServerHub.say` cleans text with `mcText` (strips `§` codes/control chars, caps 256); `broadcast`'s notice to an Agent too (caps 1 KiB). The hub never builds Factorio command text: the Agent does.
- MC → Discord: `md()` escapes markdown incl. headings/masked links (a milestone's text, player and force too, a Backup's name, as an Agent's saves are named in the game's folder, a backup's detail, and every other string an Agent sends that a post, a notice or a topic shows), and a post is cut to 2000 characters after it; the Client uses
  `allowedMentions: { parse: [] }` so nothing the bot posts can ping. A factorio player's relay webhook name is
  tagged `(Factorio)`, and one with whitespace or parentheses is posted as the bot (`relayAs`), so a name from the
  game never passes for a dashboard line or the bot.
- Services: only units listed in `integrations.systemd` are passed to systemctl/journalctl (validated unit names, after `--` or as `--unit=`, `execFile` without a shell); polkit (`deploy/orrery-hub.rules`) allows exactly those, except agent-backed services, which are never passed to them: their actions are the Agent's `serviceAct` on its own unit, their logs its `journal`, and they stay out of polkit's `UNITS`.
- New server: the id (`^[a-z][a-z0-9-]{0,31}$`) is the only request string that becomes a path or a unit name (`<root>/servers/<id>`, `<root>/java/<id>`, `<id>.service`, asked of systemd only with `show --property=LoadState --`, the one call on an unlisted unit); the start script must be a plain `*.sh` at the pack's content root; the runtime one in the table. The Mod token is random, written only to the 0600 `orrery.cfg` and `.orrery-pending.json`, and never in an API answer; `add-server.sh` treats the pending file as untrusted.
- Server logs: `GET /api/servers/:id/logs/:name` reads only a name the hub's own listing of that server's `logs/`, `crash-reports/` and `hs_err_pid*.log` holds right now (plain files by `lstat`), never a path built from the request, and opens it `O_NOFOLLOW`; `..`, slashes, unlisted names and symlinks are 404. At most a file's last 4 MB is held. A server an Agent runs has
  no folder here: its listing is the Agent's `logs` reply, and a `log` request goes out only for a name a fresh
  listing holds (else 404); the Agent checks the name against its own listing again.
- Restore: the hub passes the restore script only a backup name it listed itself, as an argument (no shell), and only while the linked service is stopped; the script re-checks both and refuses to run as root. A server an Agent runs: only a name its Agent's latest `saves` push holds goes in its `restore` request, only while its pushed service state is inactive or failed; the Agent checks both again and copies the save as the newest, overwriting nothing.
- Deploys: GitHub is read with `GITHUB_TOKEN` (env only); only a tag GitHub listed, matching `^(hub|web|mod)-v\d+\.\d+\.\d+$`, for
  its own part, ever goes into a unit name. Deploy units are outside `integrations.systemd`: only
  `<configured template>@<that tag>.service`, and only `start` (plus `show` to read it). polkit's separate deploy
  block allows exactly that; the unit's script re-checks the tag (`deploy-hub.sh` also refuses to run as root;
  `deploy-web.sh` runs as root from a root-owned copy and writes the status file as the root folder's owner). A Mod jar is written
  only into a configured server's `mods/`, under a name built from the tag.
- Packs: a zip's entries are listed (`unzip -Z`, count checked) before anything is extracted, and a symlink, an absolute
  path or a `..` refuses it; `unzip` runs through `execFile`, no shell. Every path from a request (an Extra's target, an
  edit's file) is normalised, refused if absolute or with a `..`, kept inside `dir` (symlinks resolved) and outside the
  Kept paths (the Mod's jar among them); staged files are checked the same way before the swap. Extras are stored under
  their row id, so no request path is ever a path on the hub's side. Uploads are capped at 4 GiB and chunks at 64 MiB
  (bytes counted, not `content-length`); a chunk's offset must be exactly the bytes received, and upload ids are
  random and checked against `^[0-9a-f]{32}$`, so no request names a file either. A library download sends the
  GitHub token only on the API request the hub built from an Actions artifact link (a pasted `api.github.com` URL gets
  none), only to `https://api.github.com` and never on a redirect's hop, and follows only `https:` redirects. Runtime names come from Adoptium's answer and must match `^temurin-[0-9][0-9A-Za-z.+_-]*$` before they touch a path; a request's runtime name must be one in the table. Library zips are stored by sha256
  (`library/<sha256>.zip`): a pack's name and version never become a path.
- `/cmd`: admin role check + `deferReply`. Every action on a server (commands via `runCommand`, restarts scheduled
  or cancelled) goes to the `audit` table with its actor: `discord:<username> (<id>)`, or `hub:<why>`
  (`hub:daily`, `hub:restart`) for the hub's own, or `web:<username> (<id>)` from the dashboard (chat from it too).
- Web: binds `127.0.0.1` (Caddy adds TLS in front). Login is Discord OAuth with a single-use `state` cookie; only
  members with the admin role get a session. Session ids are random, sent only in an httpOnly, Secure, SameSite=Lax
  cookie, stored hashed, and expire server-side. Every 10 minutes a request re-asks Discord, in the background, whether the user still has the admin role (with the access token from login, stored sealed with the cookie); losing it, or Discord refusing the token, ends the session, while Discord being down keeps it. Every `/api` route but login/callback and `/api/environment` (the Environment's name only) needs one. Every request
  but GET/HEAD (logout too) must also carry `Origin` = the public URL's origin (else 403) and a JSON content type
  (else 415): CSRF, alongside SameSite=Lax. The one exception to JSON is an upload's chunk, `PUT /api/uploads/:upload` (exactly
  that method and path), which takes only `application/octet-stream` (no cross-site form can send it); its Origin is
  checked all the same. Chat from the dashboard goes through `ServerHub.say` like Discord's. The OAuth client
  secret comes from `DISCORD_CLIENT_SECRET`, never config.

## Tests

`test/servers.test.ts` drives a real socket with a fake mod (`fakeMod`, `online`, `until` helpers in `test/fake-mod.ts`) — use it
for any hub behaviour change. `test/agents.test.ts` does the same for the Agent port: a fake Agent's two connections on real
sockets on 127.0.0.1 (an ephemeral port), the expected peer address set through the Agent's config `address`. `test/start.test.ts` starts a whole hub via `startHub` with a stub frontend and a fake Discord OAuth, driving the web API through `app.request` (no port). Keep timing-sensitive tests on small `HubOptions` timeouts, not sleeps of seconds.
